「万字长文」大模型异步 RL 框架的设计与权衡：从 Staleness 控制谈起

小八在coding（北大 PKU-DAIR 博士在读，2026-11-16）万字拆解异步 RL 框架的 staleness 控制：先给“严格上限”下定义（每个参训 token 的生成版本与训练版本之差 ≤ 上限），再横评 verl / TRL / AReaL / SkyRL / NeMo-RL 等 14 种配置的三层机制（L1 准入 / L2 生成中 / L3 训练前），指出只限准入的框架管不住慢轨迹（AReaL 上限设 1、实际最高到 3，50 批里 46 批超限），而严格的办法要么丢弃（浪费算力、偏向短序列）要么等待（固定批次、调度僵化）；最后提出 Reserve–Occupy 协议——把 staleness 控制变成放置问题（v_buffer ≤ v_traj + η），生成前按最差情况预留合法槽位、完成后按最好情况尽早占用，SimRL 验证 600 批零超限、零丢弃，有效吞吐在各上限下均为最高。异步 RL infra 的核心设计文，协议已在作者的 PSRL 框架中实现。

大纲

问题：异步 RL 的 staleness 是什么

  • 异步 RL 把 rollout（生成）与训练解耦并行，GPU 利用率与吞吐上升；代价是样本参训时，生成它的策略可能已是几个版本之前
  • token staleness = v_train − v_gen；来源有二：生成中跨版本（partial rollout 下一条轨迹可含 v1+v2 的 token）与生成后排队等待
  • 严格标准：设定上限后，必须保证每个实际参训 token 的 staleness ≤ 上限；平均值低或某负载下未超限都不算数

三个介入点：L1 / L2 / L3

  • L1 准入控制（生成前）：最便宜，但只限数量管不住单条慢轨迹——8 并发槽里一条长轨迹占 1 槽，别的短轨迹把训练推到 v5，它在 v0 生成的 token 参训时 staleness=5
  • L2 生成中控制（权重同步时）：检查在途轨迹、取消已不可能达标的，越早取消省的算力越多，但已生成的 token 白费；且过 L2 后排队仍可超限
  • L3 训练前控制（入队/组 batch 时）：离训练入口最近、最直接；但会带来等待或丢弃

现有框架横评：只限准入的管不住，严格的都有代价

  • 10 框架 / 14 配置对照：AReaL、SkyRL、OpenRLHF、slime、NeMo-RL ready_first 只有 L1，严格上限不达标
  • AReaL 实证：max_head_offpolicyness=1 时实际最高 staleness 到 3，50 个训练 batch 里 46 批含超限轨迹且都参训了
  • 能严格控的（verl、TRL、ROLL、prime-rl、Dressage、NeMo-RL 其余配置）靠 L3 丢弃或等待：丢弃浪费已花算力、还把保留数据偏向短序列；等待（如 NeMo-RL in_order 预绑定批次）则牺牲调度灵活性、可能卡在一个 batch 上

Reserve–Occupy：把 staleness 控制变成放置问题

  • 核心规则：每条轨迹记 v_traj，每个 buffer 标 v_buffer（它将用于哪轮训练）；上限 η 时，轨迹最终必须落在 v_buffer ≤ v_traj + η 的 buffer
  • Reserve（生成前，按最差情况）：在合法范围内偏晚的 buffer、偏后的空槽预留位置；无合法空槽就不准入
  • Occupy（完成后，按最好情况）：不固定在原预留位，而是把已完成数据挪到最早的合法空槽，未完成轨迹的预留往后推；槽位三态 Empty / Reserved / Occupied，buffer 三态 PENDING / STUCK / READY
  • 扩展：partial rollout（按最早版本 v_traj 校验）、超时丢弃预留、Occupied 筛选补位、GRPO 整组操作、组级/批次级过采样

SimRL 验证：600 批零超限，吞吐最高

  • 自研模拟器 SimRL 在同一硬件/模型/负载下复现各框架机制，与真实 verl 轨迹偏差 −1.5%
  • 设置：Qwen3-8B、8×H20、GRPO 组 8、每 batch 16 prompt × 8 = 128 轨迹、dapo-math-17k 真实 trace
  • 正确性：η∈{0..5} 各 100 批，共 600 批零超限；η=5 时实测最高仅 4；全程零丢弃
  • 有效吞吐（η=1/2/3）：1,929 / 2,007 / 2,056 tokens/s；对 in_order 约 1.11–1.14×、weight_fifo 约 1.06–1.17×、verl 最高 1.34×、TRL 1.20–1.36×、ROLL 1.28–1.33×
  • 结论：生成前预留合法位置、完成后按实际顺序调整放置，既不丢数据也不绑死批次；协议已在作者的 PSRL 框架中实现
