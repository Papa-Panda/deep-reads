“推拉”之间：DeepGEMM、Mega MoE和DeepEP通信方案简析

以 DeepSeek V4.1-Flash 的 MoE 专家并行为例，对照 DeepEP 与 DeepGEMM Mega MoE 的通信设计：为什么 dispatch 一边是推、一边是拉，而 combine 两边都是推。值得他看的是它把推拉选择归结为“写时是否知道最终地址”和“谁控制节奏”，正对 MoE 推理通信与融合 kernel 的核心问题。

大纲

大纲

  • 背景：MoE 专家并行的三步
  • dispatch：把 token 送到持有选中专家的卡
  • 两层矩阵乘法：专家计算
  • combine：结果送回原卡求和
  • 两种实现对照
  • DeepEP：只做通信，dispatch/combine 各为独立 kernel，中间由 DeepGEMM 算矩阵
  • Mega MoE：dispatch、两层矩阵乘法、combine 融合进同一个 kernel
  • 核心差异一：推与拉
  • dispatch：DeepEP 推、Mega MoE 拉；combine 两边都是推
  • 判据：写的那一刻，写方是否知道最终地址；以及谁需要控制节奏
  • 核心差异二：scatter 与 gather
  • 拉按输出行顺序取数，低编号 GEMM 块先填满、先算
  • 推按输入顺序发数，输出块零散填满；只有融合 kernel 能吃到提前开算的好处
  • 核心差异三：SM 内分工与代价
  • Mega MoE 用 warp 分工而非整 SM 分工，拉取主要靠 TMA 硬件
  • 代价：多一次计数交换、约 1.35 倍 NVLink 流量、仅限 NVLink 域内
  • 结论：两种设计在各自约束下都合理，关键是下游是否在同一个 kernel 里
