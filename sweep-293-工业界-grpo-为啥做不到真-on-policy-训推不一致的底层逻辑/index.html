工业界 GRPO 为啥做不到真 on-policy？—— 训推不一致的底层逻辑

讲工业界 GRPO 做不到真正 on-policy 的原因：训练引擎与推理引擎即使权重相同也会算出不同的 logprob，MoE 路由放大了这种训推不一致，并给出 FP16、路由回放、GSPO 与一系列工程补丁等解法。值得他看的是它直击后训练 RL 的一个真实落地痛点——不是调参问题，而是 on-policy 假设本身在双引擎架构下就不成立。

大纲

大纲

  • 起点：一个面试追问
  • 采样策略与更新策略是否严格同一
  • vLLM 采样 logprob 是否等于 FSDP 更新 logprob
  • 为什么工业界不把训推放进同一框架
  • 为什么必须双引擎
  • 训练引擎（Megatron/FSDP）：反向传播、大显存、参数同步、显存分片
  • 推理引擎（vLLM/SGLang）：高吞吐、低延迟、PagedAttention、动态批处理、KV Cache 管理
  • 两者硬件优化目标冲突，同一框架无法两头最优
  • 即使同一框架，generate 与训练前向在 mask 处理、KV Cache 使用上也不同
  • 训推不一致是什么
  • 同权重、同 token 序列，两引擎 logprob 仍不同
  • 用 K3 KL 量化训练策略与推理策略之差
  • 数值看着很小（1e-3 量级），却足以让训练实质上 off-policy
  • 为什么 MoE 更严重
  • 浮点非结合性与算子实现差异可能翻转 Top-K 路由
  • 路由一变，激活的参数完全不同，分布随之发散
  • 训练侧专家容量限制与负载均衡还会丢弃/重路由 token
  • 表现为 MoE GRPO 奖励在约 120 步附近突然崩塌，调学习率与 clip 修不好
  • 解法一：FP16 替代 BF16
  • RL 微调阶段权重动态范围已基本固定，BF16 的范围冗余、精度不足
  • FP16 尾数 10 位 vs BF16 尾数 7 位，精度约高 8 倍
  • 文中称可把训推不一致降低约 24 倍；仅 RL 阶段用 FP16，预训练仍用 BF16，需 loss scaling 防溢出
  • 解法二：路由回放 Routing Replay
  • 强制训练复现推理时路由决策，让两侧激活同一专家
  • R2 回放训练引擎原 rollout 路由，主要解决策略陈旧带来的路由漂移
  • R3 记录并回放推理引擎 rollout 路由，同时解决引擎差异与陈旧问题
  • 代价是隐式策略偏差：回放后的目标策略不再是原 pi_theta；离线程度大时 R3 表现更好
  • 解法三：GSPO，重要性比率从 token 级升到序列级
  • GRPO 在 token 级做重要性采样，而奖励是序列级的，方差随长度累积
  • GSPO 用序列级重要性比率加长度归一化，让优化单位与奖励单位对齐
  • 文中实验：Qwen3-30B-A3B-SFT 上 GSPO 在 120 步未崩塌，GSPO+R3 进一步提升
  • 兜底工程补丁（物理不一致消不掉时）
  • TIS：截断 token 级概率比
  • MIS：概率比超阈则剔除 token 或序列
  • slime 的 Veto 机制：任一 token 有问题则丢弃整条序列
  • 自归一化/批归一化：强制批内平均权重为 1，抵消有效学习率抖动
  • 延伸方向
  • 训练侧：随机 token 选择 RTS、专家聚合 AoE、辅助负载均衡损失
  • 推理侧：专家剪枝、任务级路由、Matryoshka MoE、容量感知推理（文中称约 1.9 倍加速且精度几乎无损）
  • 提醒：文中评论区有人质疑 GSPO 的定位，认为它针对 off-policy 场景，未必解决非 MoE 的 on-policy 不一致
