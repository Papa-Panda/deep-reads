大纲（全文已通读；德布劳钦，LLM Infra底层码农，编辑于 2026-10-25；64 赞 / 142 收藏）

  • 背景：为什么要用网卡搬数据
  • DeepSeek 开源推理框架 DeepInfer：命中的 KV Cache 先取到 host，再 swap-in 进 GPU，与逐层前向计算重叠
  • KV 块拷贝粒度很细，CUDA 拷贝引擎在此场景表现差
  • 改用 GDR（GPUDirect RDMA）：RDMA 网卡搬数据，跑满 PCIe 带宽，不占 GPU SM
  • 核心只两行：ibv_post_send 提交请求 + ibv_poll_cq 轮询完成
  • 一、先把整件事讲一遍：RDMA READ 是什么
  • RDMA：本端网卡直接读写对端已授权内存，对端 CPU 不参与每次传输；常用 WRITE 与 READ
  • QP（Queue Pair）是网卡上的通信端点：网卡存连接状态，host 存 SQ（主动发起请求）与 RQ（接收对端 SEND）
  • 请求方 QP0（本地 host 缓冲 H）与响应方 QP1（远端 GPU 缓冲 D），一次 READ 读 4096 字节；demo 中两 QP 在同一网卡上
  • 一次 READ 的七步：CPU 写 WQE → 敲 doorbell → 网卡 DMA 读 WQE 校验 lkey → QP0 发 READ 请求（只含地址与 rkey，无数据）→ QP1 校验 rkey、经 PCIe BAR 读 GPU 显存 → 网卡 DMA 写 host H → 写 CQE，CPU 轮询得知完成
  • 谁搬数据：网卡内的 DMA 硬件；CPU 只做控制面，GPU 拷贝引擎与 SM 均不参与
  • 二、MR：为什么要先"登记"内存
  • host 指针 H 与 GPU 指针 D 都是虚拟地址，网卡走 PCIe 总线地址，无法直接用；且 OS 可能换出/迁移页面
  • ibv_reg_mr：驱动 pin 住内存、建网卡可用映射、记录访问权限，得到 MR
  • 每次 MR 产生 lkey（本地访问凭证）与 rkey（对端访问凭证）；网卡每次访问都校验 key、地址范围与权限
  • 三、创建 CQ 和 QP，把执行条件准备好
  • 控制面 vs 数据面：登记内存、建 CQ/QP、连接 QP 只做一次；每次传输重复的 post_send + poll_cq 属数据面
  • 纠正误解：kernel bypass 指高频数据面操作不进内核，不是驱动从不参与——驱动在控制面建好受保护通道，用户态才能安全绕过内核
  • 先建 CQ（容量 16），再建两个 RC（Reliable Connection）QP；QP = 连接上下文 + SQ/RQ 两条队列
  • 连接 QP：三次 ibv_modify_qp 走 INIT（选端口、允许远端读写）→ RTR（写入对端 QPN/GID/PSN/MTU）→ RTS（设起始序列号与重试策略）
  • 术语：QPN 为 QP 编号；GID 为 RoCE 网络地址（demo 用 GID index 3，IPv4 映射 RoCE v2）；PSN 为包序列号（检丢包乱序，非应用请求号）；MTU 决定 4096 字节请求拆包数
  • 四、CPU 提交请求
  • 组装 WR：SGE（本地段地址 + 长度 4096 + lkey）、wr_id=7（应用自编号，用于匹配完成）、opcode=RDMA_READ、remote_addr=D、rkey、SIGNALED（完成时留 CQ 记录）
  • ibv_post_send：provider（mlx5）把 WR 编码为 WQE 写进 SQ，再敲 doorbell（只写网卡寄存器一个位置，不带数据）
  • 返回 0 只表示请求已入队，不代表数据已读回；WR/SGE 栈上结构可复用，但 D 与 H 两块数据缓冲在传输期间不可改写或释放
  • 五、网卡执行：从 WQE 到 DMA
  • 网卡自取 WQE、找 QP0 上下文 → 校验本地目标 H（lkey 与范围）→ QP0 发 READ 请求 → QP1 校验 GPU MR 后经 PCIe 读显存并返回 → 请求方 DMA 写 host
  • PCIe 拓扑：网卡与 GPU 是对等 PCIe 设备，经下游桥 B → 上游桥 → 下游桥 A → 网卡，读 GPU 不经过 host 内存；写 host 再经 PCIe root 与内存控制器
  • 六、CPU 查完成：CQ 如何工作
  • CQE/WC 只有元数据：哪个请求（wr_id）、哪个 QP、何种操作、成功与否，不带数据
  • ibv_poll_cq 非阻塞：返回 0 表示暂无记录；有记录 ≠ 成功，必须依次校验 status、wr_id/qp_num、opcode；多 QP 共享 CQ 时按 wr_id 与 qp_num 分发
  • 七、把所有环节串起来：完整最小伪代码
  • 准备阶段（控制面）：分配 H/D → 开设备 → 建 PD/CQ → 登记两块 MR → 建两个 RC QP → 互相连接
  • 每次传输：组装 WR → post_send → poll 直到完成 → 校验成功与匹配
  • 验证设计：D2H（GPU 填 pattern_B → CPU 清 H → READ → CPU 校验）与 H2D（pattern_A 镜像）对照；全程唯一一次 cudaMemcpy 只读 4 字节错误计数，证明走的确实是 GDR 路径
  • 拆卸顺序：先停掉未完成访问 → 销 QP → 注销 MR → 销 CQ/PD/ctx → 最后释放 GPU 与 host 内存
  • 注：§3.2 处设备名字符串页面渲染有乱码，§7 伪代码拼为 roce_vf_rail5；§6.1 一句页面渲染截断，含义（仅元数据）由上下文明确
