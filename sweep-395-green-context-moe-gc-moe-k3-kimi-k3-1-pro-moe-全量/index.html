【Green Context MoE】GC MoE K3：Kimi K3.1 Pro MoE 全量优化

木子知（2026-11-24）用 CUDA Green Context 把整个 Kimi K3.1 Pro latent-MoE 子层当作一个调度单元：计算/通信双分区 + 5 个基础角色 + 2 个条件角色按数据就绪推进，GB200 上相对 SGLang 平均快 1.13×、vLLM 快 1.37×；附 GitHub 实现与 arXiv 论文。MoE 推理调度的硬核实战拆解。

大纲

1. K3 的 latent-MoE 为什么特殊

  • 路由：7168→896 线性层，sigmoid 分数 + expert bias 选 Top16；896 个路由专家各为 3584→3072→3584 门控 MLP，SiTU 门控
  • 潜空间 7168→3584：路由专家只在降维潜空间里算；2 个共享专家直接读原始 X，可与路由分支并行
  • 精度：路由权重 FP4（K32 scale）、路由激活 FP8 E4M3，共享与上投影 BF16；输出 Y = U + S + P

2. 现状：SGLang 与 vLLM 的 Mega MoE 方案

  • 两者路由部分都用 DeepGEMM Mega MoE：一次设备调用完成路由交换 + 专家 MLP
  • SGLang：共享 MLP 放辅助流，主流跑 Mega MoE + RMSNorm + 上投影；Mega MoE 的 SM 上限为设备 SM 数 − 2
  • vLLM：门控/Top16 与 latent-down 在双流重叠，但 Mega MoE 与共享 MLP 在主流上串行

3. CUDA Green Context：一句话

  • 驱动级 SM 分区接口：把 SM 切成计算分区与通信分区，可并发执行
  • GC MoE K3：路由元数据发布与跨 rank 交换放通信分区，投影、归一化与专家主 GEMM 放计算分区；Routed Assist 开启时通信分区也可跑路由 GEMM

4. 七个角色与数据流

  • 计算分区：Front（1，合并 GEMM + 就地 FP8 量化）→ Compute（4，路由/共享 W1/W2）→ Finalize（5，FP32 加权合并 → RMSNorm → 上投影）
  • 通信分区：Router（2，Top16）→ Dispatch（3，token 交换走有界 ring）
  • 条件角色：Reduce（6，split-K FP32 分部求和）、Routed Assist（7，通信分区空闲 SM 复用跑路由 GEMM）

5. 四条优势

  • 整层一个调度单元：按任务/数据就绪推进，不按框架流调度
  • 重叠：early-shared 让 Front 两轮 TMA 后即触发共享 W1；Finalize 合并时预取上投影权重
  • 跨 rank 回收去掉尾部屏障：接收计数双缓冲跨两代，按 token 只查选中专家所在 rank 的返回 epoch
  • 数值边界显式：路由权重在 Finalize 合并处乘（Mega MoE 在 SiTU 后乘），实数相等、有限精度不等，精度校验需按各自路径算参考输出

6. GB200 实测数字

  • 24 个点（EP8/16/32 × 每 rank 1–128 token）全部快于两个基线
  • 等权平均：相对 SGLang 1.1324×，相对 vLLM 1.3651×；最佳 EP32、每 rank 2 token：128.456 µs vs 156.994 µs
  • 附 GitHub 实现 gc-moe 与 arXiv:2611.30542
