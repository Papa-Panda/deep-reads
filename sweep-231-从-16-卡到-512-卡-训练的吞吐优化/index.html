从 16 卡到 512 卡：训练的吞吐优化

知乎推荐流专栏（作者 a'晨，编辑于 2026-10-12 上海；读时 20 赞同、37 收藏、0 评论。已通读原文的更正版——本轮早先因通读报告迟到曾以未读原文兜底写入）。文章基于 Aleph Alpha 的 scaling 实践报告、用 torchtitan 在 B200 上拆 30B-A3B MoE 的训练吞吐：16 卡 FSDP=16 时 28.4k tok/s/卡、MFU 37.5%；128 卡 28.0k、37.0%；512 卡改用 FSDP=128×外层 DP=4 的 HSDP 后 26.7k、35.3%——卡数 ×32、总吞吐 ×30.1，单卡保留约 94%，按此速率 20T tokens 约 17 天。关键手法是 selective recompute 与 LBS 的联合 sweep、通信与计算重叠、以及把跨副本 all_reduce 推迟到最后一个 microstep 的 backward 才做。

  • 设置：30B-A3B MoE（总参约 30B、每 token 激活约 3B），B200，序列长度 4096，torchtitan；结果为 20 步平均，一步含全部 GA microstep 的前向+反向+优化器时间；不用 TP/PP/CP/EP
  • 全文八节
  • 训练效率的三个指标 → FSDP 与 HSDP → recompute 与 LBS → memory profile → LBS sweep → communication overlap → 128→512 GPUs → 参考
  • 三个指标先立规矩
  • TPS = 总 tokens /（墙钟时间 × GPU 数）；MFU 的 F_peak 用 B200 稠密 BF16 峰值（不用稀疏峰值），且 recompute FLOPs 不计入 F_token
  • 作者明确警告：MFU 35.3% 不等于 GPU 空转 64.7%——时间口径要看 compute busy ratio；显存口径分 reserved（热力图）与 allocated（profile）两种，不可混用
  • 主线一：显存决定 LBS，LBS 决定吞吐
  • 常驻模型状态 + 保存的激活共同封顶 Local Batch Size；扩 FSDP 组与 recompute 都在腾显存换 LBS，代价分别是更多通信与额外计算
  • 16 卡 sweep（9×15 矩阵）：无 recompute 在 LBS=6 最快但可行域极窄；selective recompute 在 LBS=18 达峰值 TPS 28,414、MFU 37.47%、显存 92.2%；LBS=22 时显存 98.6%、TPS 跌至 23,179 并出现 allocator 重试；full recompute 峰值在 LBS=34、27,784，仍略低于 selective
  • memory profile（16 卡、selective、LBS=18）：一轮前向+反向 0–3025 ms；激活在前向逐层累积、反向逆序释放，反向有 recompute/梯度/参数收集的短时峰
  • 主线二：通信重叠与它的边界
  • 前向中下一层的 all_gather 与当前层计算重叠，所示局部窗口 compute busy 约 98.8%，未被覆盖的通信约 0.756 ms（作者强调这只是局部区间长度，不是步时增量）；重叠的通信仍会争 SM 资源
  • 128 卡时前向 all_gather 已几乎填满可重叠的计算窗口——这是不再扩大 FSDP 组的判据
  • 主线三：512 卡 = HSDP + 推迟同步
  • 保持 FSDP=128，加外层 DP=4（四组各持一份完整分片副本，梯度分片跨组 all_reduce）；最终配置 selective recompute、LBS=22，得 26.7k tok/s/卡、MFU 35.3%、显存 94%
  • 跨副本 all_reduce 推迟到最后一个 microstep 的 backward：非最终步只做组内 reduce_scatter 并本地累积梯度分片，最终步才同步一次，随后做 clipping 与优化器更新；依据是同一归一化约定下 reduction 线性
  • 保留意见：512 卡 profile 中最终步 backward 出现 all_reduce 尾巴，但其采样层（0–5）与非最终步（25–30）不同，两窗口长度不可相减估算该成本；FSDP=256/512 未做对照测试，更大组是否划算仍需实测
