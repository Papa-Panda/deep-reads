在 H100 上看见 PDL：让下一个 kernel 提前启动

抖音 AI Infra 作者在 H100 上实测 CUDA PDL：RMSNorm→QKV 场景下后继 kernel 提前 152µs 启动，但端到端只快 14.6µs——他拆解了重叠被等待与竞争吃掉的 138µs，并用 3×3 扫掠证明收益成立的充要条件（producer tail 与 consumer prologue 必须双长，最高 47.3%），附 Triton launch_pdl=True 的完整映射与可复现代码。

大纲

1. 问题：kernel 交界处的空档在哪

  • 框架作者关心两件事：kernel 本身快不快，以及 kernel 之间有没有空转
  • CUDA Graph 解决的是 host 侧 launch 开销；本文解决 device 侧问题：同 stream 内两个依赖 kernel 之间的空档能否收回
  • 动机例子 RMSNorm → QKV：RMSNorm 尾部部分 CTA 先退出，SM 逐渐空闲，但 stream 调度器不会提前放行下一个 kernel
  • 而 GEMM 的前段（描述符准备、权重预取、流水线初始化）并不需要 RMSNorm 的输出 y
  • 注意：裸 launch 间隙本身很小（实验中约 1.2µs），真正的窗口是 producer 尾部执行时间 + consumer 独立 prologue

2. PDL 协议：三个动作，缺一不可

  • 动作一 producer trigger：写完 y → __threadfence() → cudaTriggerProgrammaticLaunchCompletion()，再继续 tail 工作；wait 只保证 trigger 之前写入的可见性，作者初稿先 trigger 后写 y 是数据竞争，跑之前已修正
  • 动作二 host launch：普通 <<<>>> 语法带不了属性，须用 cudaLaunchKernelEx + cudaLaunchAttributeProgrammaticStreamSerialization = 1；producer 不需要 launch 属性
  • 动作三 consumer wait：先做独立 prologue（扫权重/预取），再 cudaGridDependencySynchronize()，之后才能第一次读 y；编译器不能把 y 的预取 hoist 到 wait 之前
  • PDL 只放松 launch 时序，不放松数据依赖；且是机会性的，硬件不保证每次都重叠

3. 实验一：在时间线上看见提前启动

  • 环境：H100-SXM-80GB（132 SMs），CUDA 12.9，Nsight Systems 2025.2.1；m=64, k=4096, n=768，tail 人为拉长到约 160µs 以便看清窗口
  • nsys 六组平均：baseline gap +1.22µs，PDL gap −152.06µs，pair 总时间 776.69 → 762.05µs；输出逐元素比对 max_abs_error=0
  • gap 变负证明 consumer 的启动时间戳落在了 producer 结束之前，机制在 H100 上真实成立

4. 152µs 的重叠，为什么只换来 14.6µs

  • pair 只快 1.9%，理论上限约 19.6%；因为 consumer 自身从 615.82 涨到 754.00µs（+138.2µs）
  • 拆解：cudaGridDependencySynchronize() 中的阻塞等待 + 与 producer 尾部共驻的 SM/带宽/调度竞争 + PDL 自身调度开销
  • 模型：净收益 = min(窗口, consumer 独立 prologue) − 开销；本例 152 − 138 ≈ 14.6µs
  • 教训：demo 的 consumer 是占满全部 SM 的 132-block naive GEMM，一启动就撞上 wait，竞争吃掉了重叠

5. 实验二：把收益条件显式构造出来

  • 第二个 demo 不模拟真实算子，只留两个旋钮：producer_tail_cycles 与 consumer_prologue_cycles，两个 kernel 各只用 1 block / 128 线程以排除竞争
  • 3×3 扫掠：任一旋钮为 0，收益坍缩到噪声（prologue 为 0 → 0.9%/0.5%；tail 为 0 → 0.4%/0.3%）；两者都长时收益 31–47.3%
  • 最佳格（tail=1M, prologue=1M）：gap −504.96µs，pair 1070.35 → 564.52µs，重叠几乎 1:1 转化为端到端收益；两个 kernel 自身耗时几乎不变

6. Nsight Compute 交叉验证与 Triton 侧

  • NCU 看单 kernel 硬件计数：PDL 不改变单 kernel 速度，全部收益来自边界移动；实验二里 GPU 近乎空闲，tail 与 prologue 共驻无压力
  • 工具坑：NCU 默认 kernel replay 会序列化隔离每个 kernel，overlap 在其中消失；--replay-mode app-range 给整条链的聚合计数，但无时间轴、无逐 kernel 归属，overlap 仍需 nsys 看
  • Triton：PR #6394（2025-04-30 合并）+ SM90 以上；tl.extra.cuda.gdc_launch_dependents() 对应 trigger，gdc_wait() 对应 wait，launch_pdl=True 对应 host 侧属性；Triton 版只验证了正确性，timeline 证据来自 CUDA C++ 版

7. 什么时候值得用，怎么自己上手

  • 适用：producer 有低资源 tail（epilogue 类工作）、consumer 有足够长的真正独立 prologue、资源错峰不挤占 producer
  • 生产例：CUTLASS SM90 GEMM 内置 PDL、MoE 连续专家 GEMM、RMSNorm→QKV、Attention→O-projection
  • 优先替代：能融合就先融合（还能省一次全局内存往返）；通信/计算重叠是 NCCL/多流的维度，不是 PDL 的事
  • 复现路径：xin_tutorial task 06 的 pdl_rmsnorm_qkv 与 pdl_overlap_benefit；合并前三问：consumer 变长了吗？资源错峰了吗？稳定端到端收益超过新增复杂度了吗？
