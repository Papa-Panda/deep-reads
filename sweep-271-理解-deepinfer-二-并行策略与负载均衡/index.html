理解 DeepInfer（二）：并行策略与负载均衡

知乎推荐流专栏（作者 mingming，AI-HPC 专栏，DeepInfer 理解系列第二篇，全文已通读）。中心论点：并行决定等待出现在哪里，负载均衡决定等待能否被消掉。文章拆解 DeepSeek 开源推理框架 DeepInfer 的并行与均衡：注意力按请求做数据并行、MoE 按专家做专家并行；decode 用 Wide-EP 开到 64～128 卡而 prefill 只用小规模并行；EPLB 靠重排加副本压峰值负载；DPLB 靠请求落点与 prefill 切块对齐注意力耗时；末节讲视觉编码按 patch 数估负载。值得他看的是这条把推理 infra 的等待结构讲透的分析：两类等待（注意力后等专家分发、专家后等结果汇聚）要由两套均衡机制分别处理。

大纲

大纲（据全文通读整理，概括转述）

  • 中心论点
  • 并行决定等待出现在哪里，负载均衡决定等待能否被消掉
  • 同步推进的卡组里，最慢的一张卡决定整组速度
  • 一、多卡并行：注意力按请求分，MoE 按专家分
  • 注意力用请求级数据并行：每张卡只存自己请求的 KV
  • MoE 用专家并行：token 经路由送到持有对应专家的卡，算完加权汇聚
  • 不用头分片的原因：MLA 已把 KV 压成共享隐表示，头分片会重复存全量 KV
  • 每层 MoE 有两次跨卡交换，组内卡必须同步推进
  • 二、Wide-EP：decode 为什么开到 64～128 卡
  • prefill 用小规模并行，decode 用 EP64～128 的超宽专家并行
  • decode 步内 token 少、常受显存带宽约束，摊薄专家权重访问压力
  • 宽并行的收益随单卡请求数上升而收窄，因 KV 相关工作占比变大
  • 该部署不用 TP：切权重矩阵要 all-reduce，高负载下可能拖累吞吐
  • 三、EPLB：重排和副本各自解决什么
  • 目标是压单步峰值负载，不只是长期均值
  • 光重排不够：单个超热专家无论放哪都会超均值，必须靠副本分流
  • 在线 EPLB 五步：局部计数、轮询分流、贪心分配副本槽、大负载优先装进最空卡、权重迁移
  • 实测启示：重排是主收益，副本数要适度，过多反而增加权重访问成本
  • 四、DPLB：注意力阶段也会拖慢整组卡
  • 两类等待：注意力后等专家分发，专家后等结果汇聚
  • 最慢注意力卡往往不是最忙专家卡，移专家修不好注意力失衡
  • 因此要用请求落点让组内各卡注意力耗时尽量对齐
  • 五、prefill 与 decode 分别怎么均衡
  • prefill 可调每步切块：按上下文长度分层、按算力配额拉取、按时间预算切块
  • decode 的 KV 一旦落卡就跟随请求到结束，所以入组落点是决定性的
  • decode 要同时看请求数与总 KV 长度，只看其一都会失衡
  • 六、DPLB 与 EPLB 怎么配合
  • 分工：DPLB 管注意力工作量，EPLB 管专家工作量；动作频率不同（每步 vs 每千/万步）
  • 计算分配上近似可分，但通信路径耦合，最终以端到端吞吐评判
  • 适用边界：无共享同步进程的独立实例是排队与容量路由问题，不适用这套组同步方案
  • 七、视觉编码：按 patch 数估计负载
  • E/P/D 分离下图像先过视觉编码服务再进 prefill
  • 路由两级：机器间随机选，机内选待处理 patch 数最少的卡
  • patch 数比图片张数更贴近真实工作量，但仍是受缩放、裁剪影响的估计
