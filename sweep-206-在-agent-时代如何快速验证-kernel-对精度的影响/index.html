在 agent 时代如何快速验证 kernel 对精度的影响

知乎推荐流条目（SuSun，2026-10-19 发布，37 赞、27 收藏；原文通读，为本轮 5 条候选中深度第一）。Agent 时代 kernel 迭代太快，端到端跑分既慢又无法归因，作者提出一套可复用的合并前精度门：不比采样出的 token，而是把候选 kernel 的 logits 与固定的 f32 参考实现（厂商 modeling 代码）逐位置对比，用 KL、按 margin 分桶的 top-1 翻转率等指标定位分布漂移，并用 Qwen 混合架构上的原始实验 вскрыть 循环状态与 fp8 注意力的隐蔽精度点。对他正对口：这是 CUDA/推理优化一线方法论，结论可直接迁移到自己的训推一致性检查。注：本轮早先据一份有误的浏览器摘要误存过一条 Terminal-RSI（数据与定性均有误），已 discard 撤回，本条为更正后的知乎槽位。

大纲

大纲（据原文通读整理）

  • 问题：端到端验证跟不上 Agent 写 kernel 的速度
  • 大模型服务光启动（权重加载 + autotune/JIT）就要约 20 分钟，再跑评测又是约 20 分钟且至少 8 卡
  • 跑分变红也分不清是 PR 回归还是采样噪声，batch 不变性并不成立
  • 方法：比 logits，不比 token
  • Ground truth 固定为厂商参考实现（如 HF modeling 代码）以 f32 跑一次并落盘，永远比参考、不只比上一版，防止小误差逐 PR 累积
  • Teacher forcing 喂固定文本；判据取向是不容忍假阴性（宁可误报）
  • 三指标联用：KL（只在基线 top-20 token 上算、其余合并为 other 桶，避免尾部小概率噪声主导）、top-1 翻转率、margin（top-1 与 top-2 的 logit 差）
  • 翻转必须按 margin 分桶看：小 margin 处翻转本就常见，大 margin 处翻转才是危险信号
  • 理论诚实性：logits 指标与下游精度只是松的上界关系
  • 用链式法则 + Pinsker 可把精度差界到 KL 上，但代入正常差异量级后界松到没有判别力
  • 结论：阈值不能靠定理，只能靠回放历史精度 bug、注入合成 bug 经验校准，像给每个修过的 bug 加单测
  • 困惑度在这种量级下被证明无用，连变体排序都做不到
  • 原始实验（Qwen 混合线性注意力 + 全注意力架构）
  • 攻击循环状态：每步更新后截断尾数位，拐点在 bf16 附近；源码级发现主流实现的状态在块间本就会转 bf16 存储，f32 接口只是表象——状态存 bf16 可省一半内存带宽
  • 攻击注意力权重 P 的舍入：f32/bf16/fp8 对比；直接 fp8 随上下文变长退化（小权重下溢为 0），先放大 448 倍再量化即与 bf16 相当——误差的方向（单边下溢系统性累积）比误差大小更重要，带符号误差会互相抵消
  • 语料深度教训：短 prompt 下状态不出 prefill 内部存储，这类 bug 根本测不到；要 32k 以上分块 prefill 才暴露
  • Token 级检查被实证否决：九成以上高 KL 位置并不翻转 token，高精度变体反而可能因平局打破方向更早发散
