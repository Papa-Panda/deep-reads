Weight Resharding in RL System

NVIDIA 上海工程师讲 RL 系统里训练权重同步到推理侧的 resharding：训练（FSDP/TP/PP/EP）与推理并行布局不同，同步不是拷贝而是按元素重分片；按“全量张量在哪物化×发送方是否预筛”两轴比较各方案（NCCL vs NIXL、verl 路径），结论是按参数混用多条路径。值得他看的是它正撞 RL 训练 Infra 主线，把权重同步的通信量、临时显存、工程复杂度都算清楚了。

大纲

大纲（全文已通读）

  • 问题：RL 系统里权重同步不是拷贝
  • 训练更新 policy 后，新权重要同步给生成 rollout 的推理 worker
  • 训练与推理并行布局不同：训练用 FSDP/TP/PP/EP，推理按模型规模、吞吐、延迟另选布局
  • 同步要改变每个参数元素的归属 rank，这一步叫 weight resharding；训练侧是 source，推理侧是 target
  • 三个基本概念：逻辑张量 / 局部分片 / 物化全量张量
  • 逻辑张量：完整的数学对象（如一个投影矩阵）
  • 局部分片：某个 rank 实际持有的一部分
  • 物化全量张量：一份进程 GPU/CPU 缓冲里的完整数据
  • 知道全局形状与分片位置 ≠ 手里有完整数据
  • 难在哪：分片方式与布局错位
  • 简单情形：行切 32 份 source 分片 → 8 份 target 分片
  • 难情形：行切 vs 列切、层从 PP stage 3 移到 stage 1、专家换 owner
  • source 侧可能有 fused QKV、交错 gate/up、EP 分布专家、FSDP/DTensor 局部分片；target 侧可能要不同融合顺序、转置布局、量化权重+scale、kernel 专属布局
  • 方案比较：两条轴 + 统一算例
  • 轴一：全量张量在哪物化；轴二：发送方是否只发 target 需要的数据
  • 统一算例：4096×4096 张量 32 MiB，每 target rank 收 4 MiB；128 GiB 模型每 rank 4 GiB
  • 通信：NCCL（all-gather + broadcast）vs NIXL（all-gather + ring 点对点）
  • 框架路径：verl 的 FSDP full_tensor() 与 checkpoint-engine 路径
  • 提醒：target 收得少 ≠ source 的导出聚合消失了
  • 结论：没有唯一最优路径
  • 按参数混用多条路径（表中路径 D），权衡通信量、临时显存与维护成本
  • 连续性也影响成本：行切行主矩阵多为连续区，列切常得非连续 view，需打包或按更大 source view 读再本地转换
  • 范围限定：只讨论经 GPU/CPU 内存的全量权重同步；checkpoint、增量更新、版本切换、rollout 一致性只在影响 resharding 时间时提及
