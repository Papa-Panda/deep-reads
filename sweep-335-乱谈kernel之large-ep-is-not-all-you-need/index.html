乱谈kernel之large EP is not all you need

是小肖啊在 NVL72 上实测 DeepInfer 的 DeepGEMM MegaMoE kernel，拆解 DeepSeek V4.1 Flash decode 的 MoE 层：生产负载下 EP32→EP64/72 只快约 5%，因为每专家约 135 行已越过约 120 行/专家的阈值，权重读取不再是瓶颈，剩下的是计算、NVLink 与约 45µs 固定开销；而大 EP 的故障、同步与部署粒度成本随卡数线性增长。值得他看的是它把“EP 越大越好”的官方建议用实测和延迟模型（留出误差 2.5%–6.4%）逐项证伪，并给出按延迟预算选 EP 的四步决策法，正撞 MoE 推理优化主线。

大纲

大纲（全文已通读，是小肖啊，2026-11-03）

  • 官方主张：DeepSeek 建议 decode 用 EP64–128（Wide-EP），越大越好
  • 理由一：每卡专家少，每步权重读取少
  • 理由二：腾出的显存可放更多 KV Cache，提高 TPS
  • 验算理由二：显存账算不过来
  • V4.1 Flash 专家权重总计约 290GB，EP16 每卡约 18GB，EP64 只省约 14GB（不到 5% HBM）
  • 每 token KV 仅 890 字节，60 序列 × 1M 上下文每卡只需约 53GB；显存只决定 EP 下限（≥EP2）
  • 验算理由一：官方数据本身随负载衰减
  • DeepInfer EP8 对 EP64：64 请求/卡快约 25%，256 请求/卡只快约 6%
  • NVL72 实测：延迟随每卡 token 数呈三段曲线
  • 左侧爬升 → 平台期（读全部专家权重 + 约 45µs 固定开销）→ 缓慢上升；T=1024 时各 EP 收敛
  • 生产负载（约 270 tokens/卡/步）：EP32→EP64/EP72 只快约 5%，EP72 不比 EP64 快
  • 机制拆解：一个持久化 MegaMoE kernel，五步（dispatch → L1 GEMM → L2 GEMM → 写回 → combine）
  • 只有权重读取 ∝ 1/EP 缩小；计算、NVLink 拉取/写回、同步链基本不变
  • 每专家约 120 行阈值：超过后权重读取不再是最高屋顶，EP 再大也推不动总时间
  • 延迟模型：L = S + c·t_pair + max(权重读取， 计算， 远端传输） + combine，留出误差 2.5%–6.4%
  • 大 EP 的系统成本随卡数线性增长：故障频率与中断请求数、同步等最慢卡、部署/扩缩容粒度
  • 决策法：显存下限 → 由每用户速度目标换算每层延迟预算 → 模型算各 EP 最大吞吐 → 吞吐接近时选最小实例
