在研究编程Agent，Agent核心就几十行代码，那剩下的几万行到底在解决什么问题？

编程 Agent 的核心循环只有几十行，但 OpenHands 等开源实现有数万行代码——三位高赞答主从行数审计、工程分类、失效模式三个角度汇合，讲清剩下的代码都在解决什么：沙箱安全、上下文管理、错误恢复、模型-工具协同训练。值得他看的是它把 Agent infra 的工程量从“几十行 demo”还原为“让概率系统在生产环境确定性运行”的可靠性系统，正对 Agent harness 这一优先方向。

大纲

大纲

  • 提问：核心循环 vs 几万行代码
  • Claude Code 逆向出的系统提示：uuid 线程、每次编辑快照、子 Agent 侧链
  • 追问：核心就几十行，剩下的几万行在解决什么问题
  • 回答一：行数审计（安小强，1272 赞）
  • OpenHands 核心 Agent step() 仅 35 行，仓库约 8 万行 Python
  • 沙箱运行时 17400 行：Docker 生命周期、端口/卷/网络隔离、容器内 FastAPI 服务、1500 行 Windows 兼容层
  • 卡死检测 489 行：重复语法错误、同命令跑三次、IPython 报错循环、逐字重复的工具调用
  • LLM 调用层 3282 行：980 行多模型格式转换、875 行 llm.py（视觉/缓存/计费/溢出）、108 行 429 重试
  • 结论：沙箱=安全，卡死检测=可靠，LLM 层=兼容；每行都是真实用户踩过的坑
  • 回答二：六块工程分类（笙囧同学，1247 赞）
  • 上下文管理与代码检索：AST 依赖图、embedding 语义搜索、文件摘要缓存；检索系统 alone 超核心循环 10 倍
  • LLM 输出变可执行动作：畸形 JSON/XML 解析、十余种动作类型、模糊匹配编辑（Aider 最大模块）
  • 安全隔离：沙箱、白名单、文件权限、超时与资源限制、审计回滚
  • 错误恢复：重试、错误分类、循环检测、快照回滚、降级策略；错误路径代码远多于 happy path
  • 外部集成：多模型 API、git、IDE、测试框架
  • 隐性部分：历史压缩、成本控制、可观测性、配置系统、mock/录制回放测试
  • 结论：核心循环约占 2–3%，其余是让它在真实世界跑起来的工程
  • 回答三：失效模式与状态机（杞鋂，554 赞）
  • 极简核心真实存在：nanoagent 70 行、mini-swe-agent 100 行、46 行 Bash Codex
  • 两种失效：提前停工（500 文件任务 47 个后宣称完成）、无限循环（800+ 轮重读同一文件烧掉一周 token 预算）
  • 根因：LLM 是无状态概率机器，没有进度记忆
  • 修复：外部记忆（Claude Code TodoWrite/TodoRead）、模型-工具协同训练（system_reminder 部署-收集信号-再训练循环）、记忆/上下文系统（Rust/Tantivy 会话搜索）
  • 三家 CLI 对比：GPT-5-Codex 规划强但过度重构、Claude Code 执行忠实但 token hungry、Gemini CLI 最快
  • 第四答补充：数据面 vs 控制面（旷野，210 赞）
  • 循环是数据面；权限、预算、超时、回滚、可观测性、评测是控制面
  • 可观测性是入场券，评测即 CI 才是护城河
  • 共识：循环是想法，剩下的 99% 是让概率系统确定、安全地跑在生产环境
