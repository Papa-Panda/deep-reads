RL Infra: 我们如何在 Molt 中解决多图片、长轨迹的内存瓶颈

知乎推荐流专栏（作者 初七9527，编辑于 2026-09-02；74 赞同、75 收藏。已由登录浏览器通读原文更正——本条先前据未读原文兜底写入）。一篇定位极准的 RL Infra 实战：OSWorld rollout 的 batch 从 128 提到 1024 时，GPU 还没吃饱，controller 的 CPU 内存先爆——根因不在 batch 本身，而在数据通路：所有轨迹都经 controller 中转，使只该做调度的它变成全集群的图片仓库。Molt v0.1.3 的解法是给 Experience 加 offload/reload：重字段（图片、多模态输入、attention mask、log_probs 等）在生产端经 Ray 对象存储卸载、只留 heavy_ref，controller 只收轻字段（reward、轨迹长度、group id）做过滤与调度，训练 rank 真正计算时再按引用取回。对他做 Agent RL / 长轨迹训练的人，这条『瓶颈常在数据通路、不在模型』的判断值得记。

大纲

大纲（据原文通读整理）

  • 条目信息
  • 知乎推荐流专栏，作者 初七9527，专栏「RLHF & o1 碎碎念」，编辑于 2026-09-02；74 赞同、75 收藏
  • 对象：RL 框架 Molt v0.1.3，场景为 OSWorld 的 Agent RL rollout 扩展
  • 症状与根因：内存爆在 controller
  • 每步产生新截图，轨迹越长，图片、token、attention mask、log 概率与多模态张量一起膨胀
  • 旧通路：rollout worker 生成完整 Experience → controller 收集 → 再转发训练 worker
  • batch 128 正常，提到 1024 时 controller 内存先于 GPU 饱和触顶；加 rollout 节点只会让它死得更快
  • 绕过的三条路（均被否）
  • 把 batch 退回 128：能跑但慢、不可扩展
  • 压缩图片、截断轨迹、少留截图：省内存，但等于为系统改训练数据
  • 另建专用存储服务：可行，但服务、协议与数据生命周期复杂度全涨
  • 关键 reframing：controller 不需要看见图片
  • 过滤、分组、负载均衡只需小字段：reward、轨迹长度、group id
  • 重张量只有训练 rank 真正前向时才需要 → 原则：重数据留在生产地，controller 只拿引用
  • Molt 的机制：offload / reload
  • Experience 增加 offload()/reload()；重字段经 ray.put 进 Ray 对象存储后从对象中清空，只留一个 heavy_ref
  • controller 收轻量 Experience（轻字段＋heavy_ref）照常过滤调度；样本分到某训练 rank 后，该 rank 调 reload() 按引用取回重数据
  • 数据通路从「生产→controller→消费」变为生产直达消费，controller 只传句柄
  • 为什么对 OSWorld 有用与代价
  • 不减少图片数量，改变的是放置：重数据分散在各 rollout 节点的对象存储里，系统上限从单机内存变为集群总内存与网络
  • 提醒一：节点内是 Ray 共享内存对象存储，跨节点仍要传数据，并非全局共享内存
  • 提醒二：heavy_ref 只是运行时引用、非持久化数据库；runner 重启或热恢复时未消费样本需额外的落盘与恢复处理
  • 结论
  • 瓶颈既不在模型也不在环境，而在一条看起来很自然的数据通路
  • 扩展有时不是加机器，而是别让所有数据先过同一台机器
