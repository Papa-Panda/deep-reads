PagedAttention 与 RadixAttention：KV Cache 的两场救赎

Arthur（芯片公司 AI Infra 工程师）把 PagedAttention 与 RadixAttention 两篇奠基工作放进同一框架讲透：前者借操作系统分页思想解决 KV 显存碎片化（利用率 20%→约 99%，吞吐 2–4×），后者用基数树复用历史前缀、省掉重复 prefill（多调用任务最高 6.4×）；附 V1–V4 纯 Python 模拟器实测数据与 vLLM / SGLang 源码学习路径，正撞推理优化主线，适合当作推理引擎的案头手册。

大纲（全文已通读；Arthur，芯片公司 AI Infra 工程师；专栏「AI框架」，2026-10-14 更新；28 赞 / 63 收藏）

  • 问题的根：KV Cache 三大特性
  • 巨大：OPT-13B 每 token 800KB（2×5120×40 层×FP16），2048 token 约 1.6GB
  • 动态增长：逐 token 解码，长度事先未知，分配困难
  • 前缀可复用：同一 token 序列的 KV 在不同请求间完全相同
  • 由此生出两个问题：显存碎片化（特性 1+2）与前缀重复计算（特性 3）
  • PagedAttention：管「显存怎么放」（空间维，vLLM，SOSP 2023）
  • 借操作系统虚拟内存分页：KV 切成 16 token 固定块，逻辑块连续、物理块任意离散，块表记录「逻辑块 N → 物理块 M」
  • 传统连续预分配利用率仅 20.4%~38.2%，分页后约 99%，吞吐 2–4×
  • 块级共享：并行采样共享 prompt 物理块，Beam Search 共享中间块；写共享块用 Copy-on-Write，引用计数归零即释放
  • 显存耗尽：序列级抢占，换出到 CPU 或重算（KV 计算确定故重算结果相同），FCFS 保公平、永不 OOM
  • 局限：本身不做跨请求自动复用（仅人工预留前缀）
  • RadixAttention：管「前缀怎么复用」（时间维，SGLang，NeurIPS 2024）
  • 基数树索引全部历史 KV：节点存变长 token 段，match_prefix 找最长共享前缀，只 prefill 剩余部分
  • 三操作：匹配、分裂（半段命中时拆节点）、插入；驱逐只动 LRU 叶子且 lock_ref=0 的节点
  • Cache-Aware 调度：按最长匹配前缀长度排序，让同前缀请求成批命中，避免缓存抖动
  • extend kernel：混合读连续与分页 KV，一次处理 prefill/decode 边界；多调用任务最高 6.4×
  • 殊途同归：现代引擎的两层架构
  • vLLM = 分页 + 哈希前缀缓存 APC（v0.11 起默认 sha256，cache_salt 做多租户隔离，只缓存完整块）
  • SGLang = 分页内存池 + 基数树 + cache-aware 路由；实现路径不同，终点一致
  • 代码验证：V1–V4 纯 Python 模拟器（无 GPU 依赖）
  • V1 碎片化：利用率 20.4% → 83.7%（4.1×），预留空间省 75.6%
  • V2 共享：并行采样 192 → 72 块（省 62.5%），Beam Search 148 → 62 块（省 58.1%）
  • V3 基数树：多轮对话累计省 64.3% prefill；100 请求共享 512 token 系统提示命中率 99.0%，prefill 省 94.8%
  • V4 双引擎：prefill 5965 → 2688 token（省 54.9%），代价是 KV 峰值 +25%（缓存要占显存，故需 LRU 驱逐控量）
  • 选型与学习路径
  • 单次独立调用：分页就够；多调用（Agent、RAG、多轮对话、few-shot、JSON 结构化输出）：前缀缓存是吞吐关键
  • 论文 arXiv:2309.06180 / arXiv:2312.07104；源码 vLLM block_manager、SGLang radix_cache.py（约 600 行）；复现 V1–V4；生产验证 vllm serve --enable-prefix-caching 与 sglang launch_server 对比
