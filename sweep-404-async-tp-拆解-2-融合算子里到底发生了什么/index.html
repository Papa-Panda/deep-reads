Async TP 拆解（2）：融合算子里到底发生了什么

Mxandre（2026-11-11）逐行拆解 PyTorch 的 fused_all_gather_matmul / fused_matmul_reduce_scatter：不写新 GEMM 核，只靠 stream、对称内存、barrier 与 channel 四件套重排 aten.mm 与拷贝，让通信与计算重叠；单卡模拟 1.33–1.48×，并坦言稳定性取舍与未覆盖的真实多卡验证。通信-计算重叠的硬核实战拆解。注：知乎页为摘要，全文在作者博客。

大纲

1. 目标：边算边取，不要先等再算

  • Column 线性层：每张卡算自己的 token，同时拉别卡的 token
  • 传统做法：先阻塞 all-gather，再做 GEMM，通信时间纯浪费

2. 四个前置概念

  • stream：GPU 的任务队列，拷贝与 GEMM 并发的前提
  • symmetric memory：组内每张卡可直接读写对方显存
  • barrier：信号板 CAS 0→1→0，管住先写后读、先读后复用
  • channel：信号板的不同行，隔离不同用途的 barrier；GroupStreamGuard 串行化同组 barrier

3. 融合算子没有新 GEMM 核

  • torch.library 注册于 torch.ops.symm_mem，只重排 aten.mm.out 与 copy_
  • 拷贝走 copy engine（cudaMemcpyAsync），不占 SM

4. all-gather 流水线：三道 barrier

  • 上轮数据读完 → 各方上传完毕 → 本轮读完
  • 双 stream 按 (step+rank)%R 交替，避免单卡被所有人同时读
  • 每片 GEMM 结果直接写进分块输出视图，无 cat
  • 刻意放弃部分重叠：首个本地 GEMM 等上传 barrier 之后，稳定性优先

5. reduce-scatter 改写成 all-to-all + 本地求和

  • 每块独立、可流水线；代价是 R 倍输出显存与 fp32 累加后一次舍入
  • 对比 NCCL ring：每跳依赖上一跳，无法这样拆
  • 双缓冲 buf0/buf1 绑定 stream/channel 奇偶；torch.cuda._sleep(100) 是无奈的调度 hack

6. 单卡模拟与局限

  • RTX 4060 笔记本：算力主导时 1.33–1.48×，拷贝主导时 1.25×；输出完全一致
  • 未覆盖：真实 NVLink、跨卡 barrier、reduce-scatter 双缓冲实测
  • 开放问题：GroupStreamGuard 为何串行化 barrier；中间 barrier 是否真需 channel 1
