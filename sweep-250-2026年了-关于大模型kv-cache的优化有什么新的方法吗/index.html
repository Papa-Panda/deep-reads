2026年了，关于大模型kv cache的优化有什么新的方法吗？

知乎推荐流首选（登录态核验为账号 971775；回答已经登录浏览器通读）。作者菽陌松囿，2026-10-27 发布，23 赞同、26 收藏；问题 78 人关注、8,994 次浏览、共 8 个回答。这篇不走 token 剪枝的算法路线，而是从系统层盘点 KV Cache 优化的七个新方向：存储介质三层设计与 GDS/GDR 无状态化、3FS 与 Mooncake 两类存储系统、传输侧 prefetch 与 PD 分离的小包打包、链式哈希带来的淘汰依赖、长输入的并行切分、部分前缀匹配的 cache edits、量化加压缩，以及在架构层把单 token 的 KV 做小——据作者称 DeepSeek V4.1 靠 KV 复用与 SWA 回放把 1M 上下文的 KV 压到约 1GB。与今早入清单的 Mooncake 推理实战正好互补。

  • 条目信息
  • 知乎推荐流问题下的回答，作者 菽陌松囿（8,753 关注者），发布于 2026-10-27 08:44、编辑于 08:53，上海；23 赞同、26 收藏、1 评论
  • 问题背景：提问者认为知乎上还是「过去那一套」，且 Sparse MLA 等新架构出现后应有一波新的 KV Cache 优化；本答以清单体回应，自述是「我关注到的一些点」
  • 总体取向：系统与基础设施层，而非 token 剪枝类算法；全文七个方向，无正式基准数据（仅第 7 点给出 DeepSeek 的量级数字）
  • 一、存储介质：三层设计与无状态化
  • 现状分工：存储侧用主机内存 + SSD，推理侧用 HBM + 主机内存，合称 L1/L2/L3 三层设计
  • 驱动力：海量请求下 H2D 拷贝昂贵；方向是直接走 GDR/GDS，把推理做成无状态服务以便横向扩展
  • 变量：HBF 出现后，KV 的本地化与调度可能要重新考虑
  • 二、存储系统：3FS 对 Mooncake
  • DeepSeek 用 3FS（中心化文件系统，元数据服务为树形结构）：不怕海量小文件，高可用、最终一致与容灾完备，但维护复杂
  • 开源侧多用 Mooncake 等 KV 存储（作者判断其尚在发展初期），提供 SDK 接入；3FS 则支持 FUSE + usrbio
  • 数据模型天然合 KV：键是按页切分的 token 列表哈希，值是 KV 特征，量级约 MB
  • 三、传输：prefetch、PD 间打包与 dualpath
  • Mooncake 用 Transfer Engine 或 NVMe-oF 先把远端 KV 搬到推理侧主机内存；跳过中间层走 GDS/GDR 可改善 prefetch 的延迟与带宽
  • Prefill/Decode 分离间的小尺寸 KV 对 RDMA 不友好，打包方式与如何结合 TCP 是可优化点
  • dualpath：decode 侧在 prefill 阶段也做预取，形成一定重叠
  • 四、淘汰：链式哈希的前后依赖
  • KV 的哈希是链式的：当前页哈希依赖上一页哈希作为摘要一部分
  • 淘汰策略若不处理这种前后依赖，会伤命中率——作者明确存疑现有方案是否考虑过这一点
  • 五、并行策略：长输入的切分
  • Prefill 长输入：CP + 按层切分削减显存，或用 PP；Decode 侧用 DCP
  • 六、Cache edits：部分前缀匹配（原文此点与下一点同标为 6）
  • 受 CC 系统启发：推理引擎可对 KV 做 edits，不要求完整前缀匹配、部分匹配也能命中，以此抬高命中率
  • 六（续）、压缩：量化 + 压缩换空间
  • 先分析 KV 浮点值的分布，再做量化 + 压缩，本质用计算换空间
  • 代价是 CPU 开销偏高，这部分逻辑可能要落到 C++/Rust 实现
  • 七、架构创新：从源头缩小单 token KV
  • 手段：KV 复用 + SWA bound replay（以 DeepSeek 为例）
  • 据作者称：DeepSeek V4.1 做得较彻底，1M 上下文的 KV 约 1GB；作者由此推断其「3 倍盈利空间」的说法并不夸张（此为作者推断，非实测）
  • 为什么值得看
  • 一张系统层的 KV Cache 优化地图：介质、存储、传输、淘汰、并行、命中、压缩、架构八个切面各给了一个当前进展坐标
