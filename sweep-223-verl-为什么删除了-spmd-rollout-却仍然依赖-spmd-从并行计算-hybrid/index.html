veRL 为什么删除了 SPMD Rollout，却仍然依赖 SPMD？——从并行计算、HybridFlow、Ray WorkerGroup，到Server Mode 的技术思想史

知乎推荐流条目（万理的探求者，发布于 2026-10-15，专栏「AI技术思想史」；读时 9 赞同、21 收藏、0 评论；已通读原文，更正版——先前版本作者与数据有误）。一篇 16 部分、58 节的 veRL 架构思想史：起点是 v0.7.0 的一处表面矛盾——release notes 删掉 SPMD Rollout，架构文档却说 Model Engine 仍以 SPMD 运行。文章从 SPMD 的历史与 rank/集合通信讲起，经 HybridFlow 的双层数据流、WorkerGroup 如何把 SPMD 藏进 Worker 抽象，再到多轮 Agent 的长尾如何冲击旧 Rollout、Server Mode 如何按请求调度，并专门辟一节摆四个反例（单轮大 batch 未必受益、Server Mode 不自动消除 GPU 空闲等）。结论：SPMD 没有被淘汰，只是被放回适合它的位置。

大纲（据原文通读整理，2026-10-22 更正版）

  • 条目信息
  • 知乎推荐流专栏，作者万理的探求者，发布于 2026-10-15（北京），所属专栏「AI技术思想史」2026-10-17 更新；读时 9 赞同、21 收藏、0 评论
  • 全文 16 个部分、58 个编号小节，文末附 20 项原始史料与源码出处
  • 起点：一处表面矛盾
  • veRL v0.7.0（2026-01-05）的 release notes 写明删除 SPMD Rollout 模式
  • 同一版本的架构文档却说 Model Engine 以 SPMD 模式运行——删与留为何并存
  • 易混概念先分清：SPMD 不等于同步 RL，Server Mode 不等于 Off-Policy，rollout.mode: async 也不等于完全异步 RL
  • SPMD 的来历与根基（第一至三部分）
  • 从 1980 年代并行计算讲起：SPMD 是同一程序跑多份数据，rank 是进程身份而非 GPU 编号，按 rank 分支仍是 SPMD
  • 真正的硬约束在集合通信：组内所有 rank 必须共同调用，否则死锁——许多超时与卡死的根源
  • 分布式训练天然适合 SPMD：DDP 靠 AllReduce 平均梯度，FSDP 分片后靠 AllGather/ReduceScatter，Megatron 的 TP/PP/EP 同样运行在 SPMD 编程模型下
  • HybridFlow 与 WorkerGroup（第四、五部分）
  • RLHF 不是一张计算图，而是由多个大型分布式组件构成的高层数据流：生成、算奖励、算优势、更新，构成控制流；模型内部是计算流
  • 纯单控制器粒度太细、纯多控制器与后端耦合太深；HybridFlow 的答案是高层单控制器编排、低层多控制器 SPMD 执行，另有 3D-HybridEngine 优化训练/生成两种并行布局间的参数重排
  • WorkerGroup 把一组 Ray Actor 包装成一个逻辑 Worker：trainer 代码近似本地调用，背后是 Dispatch→Execute→Collect；@register 记录分发语义，ONE_TO_ALL 广播、DP_COMPUTE_PROTO 按 DP 组切分 batch，后期又加入理解 TP/DP 拓扑的 mesh-aware 分发
  • 小结：WorkerGroup 没有替代 SPMD，它是 SPMD 之上的控制入口——它负责分发，SPMD 负责计算
  • 旧 SPMD Rollout 与 Agent 的冲击（第六、七部分）
  • 旧式 Rollout 是 trainer 对 WorkerGroup 的整批调用：生成完一整批再返回，引擎内部虽有连续批处理，瓶颈在外层批调用接口与生命周期
  • 多轮 Agent 把生成变成「生成—调工具—再生成」的循环：工具调用走 CPU/IO/网络、时长参差，长尾被放大（一个 agent 等测试 20 秒，其余早已空转）
  • 文章强调这不是 SPMD 的数学必然：问题在旧接口把请求调度与环境交互攥在自己手里
  • 2025 年的源码与 Issue 实录（第八部分）
  • AgentLoop 先行改变边界；随后有人公开质疑 Server Mode 是否真的更快（均匀请求下按数量分发近似预先均分）
  • 旧 SGLang 驱动的三个具体瓶颈：数据先汇聚到 TP rank 0 再经中间层转交调度器、驱动对象难以独立进程调度、barrier 等待造成长卡顿
  • 迁移并非一个 PR 完成：有提案被关闭未合并，原生 HTTP server 集成与默认模式切换分步落地，最终由后续 PR 把默认 Rollout 切到 Server Mode，删除记录落在 v0.7.0
  • Server Mode 怎么运行（第九部分）
  • 以一个 Coding Agent 的完整调用链为例：Trainer 取 Prompt Batch → AgentLoop 管理器/Worker → 多个 run() 协程 → 客户端把请求交给生成 server → 返回 token 后 agent 调工具并循环 → 输出汇总回 trainer 算奖励与优势、更新 Actor
  • 协程的价值在等待工具时让出 GPU 服务别人，前提是工具调用本身真正非阻塞
  • 负载均衡与粘性会话是一对权衡：首次按负载选 server、后续粘住同一 server 复用前缀缓存，缓存局部性与全局均衡不可兼得
  • 输出必须带 token mask：模型生成的 token 记 1、工具返回的观测记 0，PPO/GRPO 不能把工具文本当作策略自己的动作来训练
  • 为什么替代不了 Model Engine（第十、十一部分）
  • Server 解决的是请求调度，不是分布式梯度计算：把每个 GPU 包成 HTTP server，等于让 RPC 站上每一层 AllGather/AllReduce 的热路径
  • 一个生成 server 的内部同样可以跑 SPMD——「Rollout 接口是 Server Mode」与「模型执行是 SPMD」同时成立
  • 模式不等于独占 GPU：训练与生成可同组 GPU 共置（靠休眠/唤醒管理显存）也可分开部署；进程分离、资源分离、训练—生成异步是三个独立维度；权重布局不同（训练分片 vs 生成分片）使权重传输与重排成为独立问题
  • 四种「同步/异步」别混（第十二部分）
  • ① SPMD 内部的集合通信同步；② Agent 请求层面的异步执行；③ 一轮迭代里 Rollout 与训练是否同步等待（请求并发不改变迭代仍在策略同步）；④ 完全异步 RL——采样与训练真正重叠，代价是策略陈旧度、重要性采样与回放队列等一整套新问题
  • v0.7 为何终于删（第十三部分）与四个反例（第十四部分）
  • 官方理由指向任务形态：从单轮静态任务转向多轮、动态、交互式 Agent 任务后，旧接口不应再 owns 请求调度与环境交互；配套出现权重传输与数据传输的新组件
  • 反例一：单轮、大 batch、无工具的规则任务，旧批接口未必低效，Server Mode 的收益主要是控制边界更灵活而非速度
  • 反例二：SPMD 理论上也能实现队列与事件循环，迁移的实质是不再维护旧包装层、转而复用成熟的推理引擎 server
  • 反例三：有 Issue 记录 Server Mode 下 GPU 长时间 0% 利用——它不自动消除空闲
  • 反例四：同步 PPO 的长尾还在——99 个 agent 完成、1 个慢，trainer 仍要在 batch 边界等待；根治要走向一步偏策略或完全异步，并引入陈旧度问题
  • 结论（第十五、十六部分，四层回答）
  • SPMD 作为编程模型没有被淘汰，仍活在 PyTorch Distributed、FSDP、Megatron 里
  • HybridFlow 从 2024 年起就不是纯 SPMD：历史是高层控制与低层执行早早分家
  • 真正被淘汰的是与整批生成和 WorkerGroup 执行紧耦合的旧 Rollout 接口
  • Server 内部仍可运行 SPMD——SPMD 被放回了更适合它的位置
