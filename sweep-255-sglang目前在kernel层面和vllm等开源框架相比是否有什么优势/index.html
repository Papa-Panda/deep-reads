SGLang目前在kernel层面和vLLm等开源框架相比是否有什么优势?

知乎推荐流回答（已登录浏览器通读核验：作者刘景初，清华大学信息与通信工程博士，2026-10-27 发布，11 赞同、9 收藏；页面标注含 AI 辅助创作）。借 DeepSeek V4.1 这一轮检验一个判断：开源推理框架的 kernel 终将趋同，但趋同只发生在有官方 kernel 覆盖的平台上——SM100 上 SGLang 与 vLLM 用的是同一批 DeepSeek 开源 kernel，差距只剩融合细节且收益很小；而在官方不覆盖的 Hopper、SM120 这类平台上，谁先补上算子谁就更快，差距可以拉到数倍。值得做推理框架选型的人看：它把“框架之争”还原成了“平台覆盖 + 补丁速度”之争。

  • 检验对象：趋同说是否成立
  • 高赞观点是 kernel 各有胜负、最终趋同；本回答用 DeepSeek V4.1 这一轮看趋同发生在哪、差距留在哪
  • 趋同点：SM100 上两家用同一批 kernel
  • V4.1 的关键 kernel 均由 DeepSeek 开源、两家直接集成：稀疏注意力 FlashMLA、Mega MoE、Mega mHC 的 DeepGEMM、TopK 的 DeepSelect、通信 DeepEP
  • 剩余差距只在融合细节，收益很小：SGLang 让 mHC 把 FP8 激活直接写入 Mega MoE 输入缓冲，每 decode 步省 0.02～0.05 ms；vLLM 把 DSpark 置信头 4 个小 kernel 融成 1 个，kernel 本身快 1.9 倍，但 TPOT 提升不到 0.05%
  • 差距点：官方不覆盖的平台差距很大
  • FlashMLA 于 9 月 30 日去掉 Hopper 支持后，SGLang 自研 Hopper 路径使 8×H200 单卡输出吞吐提升 2.1～2.3 倍
  • 但在 8×H20-3e 的社区对比中，SGLang 对 DeepInfer 社区 Hopper 移植版随上下文长度翻转：8K、16K 输入时领先 19%、6%，32K、64K 时落后 16%、26%
  • 原因在 indexer：SGLang 的 SM90 indexer 对全部可见前缀打分，64K 时每 decode 轮 9.4 ms；移植版只对候选块打分，1.0 ms
  • 格式也会影响 kernel
  • SGLang 起初只在 SM100 用 V4.1 的 KV 格式，其他 Blackwell 卡用旧 V4 格式
  • 对齐 DeepInfer 的 V41_FORMAT 后，SM120 上每 token 压缩 KV 从 584 B 降到 288 B，decode 注意力耗时从 16.1 µs 降到 10.0 µs
  • 结论
  • 有官方 kernel 的平台差距极小；Hopper、SM120 这类无覆盖平台，拼的是谁先补算子
  • 文末指向作者的长文《DeepInfer 后，社区推理框架何去何从？》
