从混合 Batch 到 GPU Kernel：读懂 vLLM 与 SGLang 的 Attention 执行

讲 vLLM 与 SGLang 如何执行一轮混合 batch 的 Attention：从 chunked prefill 调度、变长张量与分页 KV，到 FlashAttention/FlashInfer 的后端组织、FA3 PackGQA 源码案例、CUDA Graph 复用与后端选择规则，并给出性能对照与调优排查顺序。值得他看的是它把推理 infra 从“调哪个后端”还原为调度、后端、kernel 三层分工的定量问题，且对引用数据的适用范围做了明确标注，正对推理优化主线。

大纲

大纲

  • 立论：一轮推理的三层分工
  • 调度决定本轮算哪些 token，后端决定 Attention 如何组织，kernel 决定 GPU 如何执行
  • 一个 batch 不把三层合并成一个决策
  • §1–3 调度与张量：混合 batch 如何成立
  • chunked prefill：长 prompt 分轮推进，后 chunk 复用前 chunk 的 KV
  • 区分三个量：B（本轮请求数）、T（本轮新 query token 数）、Lᵢ（各请求 KV 长度）
  • 变长输入用 cu_seqlens / block_table / slot_mapping 描述边界与分页 KV
  • §4–7 后端与 kernel：FlashAttention 与 FlashInfer
  • FA：统一变长接口一次交出整个 batch；FlashInfer：decode 与 prefill 分阶段调用
  • 一次调用不等于一个 kernel；同流提交按序执行，不保证 prefill 与 decode 重叠
  • split-KV：长 KV、少 query 时沿 KV 维切分并行，合并须处理归一化
  • FA3 源码案例：PackGQA 下单 query decode 每 KV-head 组有 4 个有效计算行
  • §8 CUDA Graph：动态 batch 与图复用
  • 1、2、4、8……是预捕获的执行尺寸桶，实际输入 padding 到桶后重放
  • 相同 token 数不保证复用同一张图：B=32 decode 与 B=1 prefill 的边界与任务组织不同
  • 图可复用，输入数据仍每轮原地更新
  • §9–10 后端选择：vLLM 与 SGLang 的规则
  • vLLM：按硬件与注意力类型定优先级，再逐项校验 dtype、head size、架构
  • SGLang：Hopper 默认 FA3、Blackwell 默认 trtllm_mha，MLA 与投机解码另有分支
  • prefill 与 decode 后端可分别配置；复合后端按当前 query 的注意力语义路由
  • §11–12 性能与调优
  • 先看瓶颈再比数据：TTFT、ITL 分布、带延迟约束的吞吐
  • token budget 不等于执行成本：同为 1 token decode，1K 与 128K 上下文读的 KV 差百倍
  • 三类“块”别混淆：KV 页、Attention tile、prefill chunk
  • 排查顺序：排队看负载与 KV 容量，单轮慢看 batch 形态，偶发卡顿看长 prefill

流程图

graph TD A[一轮推理：decode 与 prefill 合批] --> B[调度：决定本轮算哪些 token] B --> C[线性层按 token 维合批] B --> D[Attention 按请求边界隔离] D --> E[FlashAttention 统一变长接口 / FlashInfer 分阶段调用] E --> F[任务切分：span + block table + split-KV] F --> G[FA3 PackGQA：单 query decode 也有 4 个有效行] G --> H[CUDA Graph：按桶 padding 复用] H --> I[后端选择：vLLM 优先级 / SGLang 默认策略] I --> J[调优：先定瓶颈，再比数据]
