Agent 负载一直在变，PD 分离的推理集群怎么跟着变

momo（2026-11-17）解读 Georgia Tech 等的论文《Evolving Infra: Agent-Adaptive LLM Serving at Scale》：Agent 负载下最优 PD 配比随任务类型与负载混合漂移，固定配比最多损失 24% 吞吐；Evolving Infra 用免重启换角色、按活跃分支引用计数的 KV 驱逐与在线拟合的延迟模型，在 36 张 GB300 上相对 NVIDIA Dynamo 达到 1.10–2.73 倍吞吐。正撞 Agent infra 与推理优化主线。

  • 论文与结论总览
  • 解读 Georgia Tech 等 11 月 arXiv 论文《Evolving Infra: Agent-Adaptive LLM Serving at Scale》
  • 9 节点 36 张 GB300、9 组稳态设定：吞吐 1.10–2.73× NVIDIA Dynamo；相对离线最优固定配比，稳态最高 +38%，负载变化时 +28%
  • Agent 负载为什么特殊
  • 最优配比因任务而异：Putnam（mini-SWE-agent 解数学题，decode-heavy）2P7D；OSWorld（电脑操作 Agent，每步加截图，prefill-heavy）6P3D；CC（真实 Claude Code traces，混子 Agent 与上下文压缩）4P5D
  • 配比随时间漂移：3 小时实验里最优配比每 10 分钟从 3P6D 移到 7P2D，全程用最优固定 5P4D 最多损失 24% 吞吐
  • KV 复用不像普通对话：fork、子 Agent、上下文压缩让每个分支成独立上下文；子 Agent 调用后平均等 359 秒，下次请求仍 98% 命中 KV；压缩后 12 秒后来，但仅 14% 命中——KV 有没有用取决于还有没有活跃分支引用它，而不是多久没被访问
  • 现有系统三处失效
  • 换角色代价：Dynamo 每次换角色重启 worker，平均 681 秒（本实验 754 秒）节点不服务；Arrow 原地切换几乎不耗时，但 1 小时切换 34 次、丢 55.5% 可复用 KV；Evolving Infra 只切换 1 次、0.7 秒、丢 0.3%
  • 规划器信号太粗：Arrow 按输入全长估 prefill 时间，把缓存命中的前缀也算成待做工作，漂到 8P1D；Dynamo 看 prefill 队列长与 decode KV 占用，漂到 2P7D；两者吞吐 1.7 / 2.5 req/s，比最优固定配比 4P5D 的 4.9 req/s 低 65% / 49%
  • 路由与驱逐误判 KV：固定 4P5D 下 SGLang 网关缓存感知/粘性路由 P95 TTFT 27s / 34s；Dynamo KV 路由 65s；加共享 CPU 内存池反升至 95s（取回只在 prefill 开始后才进 HBM，时间叠加而非重叠，且副本挤占仍需的 KV）；LRU 留着压缩掉的历史、删掉等工具/子 Agent 的分支 KV；CC 上 Dynamo 的丢失 KV 复用中 39–46% 来自驱逐、15–22% 来自路由
  • Evolving Infra 三件套
  • 解耦算力分配与 KV 管理：改造 SGLang 单调度循环同时支持 prefill/decode，Mooncake RDMA 双向传 KV，全节点 CPU 内存组成与角色无关的共享 KV 池；切换时排队请求迁到同角色节点、在途请求原地跑完，直接切换不重启
  • 跨节点取 KV 藏进排队里：prefill 节点缺 KV 时 RDMA 直取对方 CPU 内存，全程在请求排队时完成；CC 126 agents 时 92% 的取回 <16K tokens、中位 7ms，64K–128K 取回中位 129ms，远小于 0.7–2.2s 的排队时间；decode 节点只写池、不读池
  • CPU 内存够不够：GLM-5.2 用 MLA，FP8 KV 约 50KB/token，单 GB300 节点约 1TB CPU 内存可存约 2000 万 token 的 KV（单份）
  • 按活跃分支引用计数驱逐：路由器维护集群级 KV 前缀树，另记每块每节点被多少活跃分支引用（需框架配合：请求带分支 ID、分支结束上报、压缩后版本号递增）；fork/开子 Agent 给复用块 +1，同分支追加只给新块 +1，压缩释放被丢块，分支结束释放全部；先驱逐零计数块（其间用 LRU），仍有引用的块最后才动
  • 在线拟合的延迟模型：prefill 单步时间 = 固定开销 + c1×未命中 token 数 + c2×QK 对数 + c3×从 CPU 恢复的 token 数（m 命中 + n 未命中需 n·m + n(n+1)/2 个 QK 对）；decode 单步时间 = 固定开销 + d1×选中路由专家比例 + d2×批内请求数；warmup 期非负最小二乘拟合后冻结，GB300+GLM-5.2 上 prefill 平均误差 4.2%（单请求）/ 6.3%（2–8 批），1 分钟内收敛
  • 规划器与路由器：每 10 分钟评估全部配比，某配比吞吐取 prefill/decode 两侧较小者；窗口切 10 个 1 分钟片，候选配比均值增益超两倍标准误才采纳，切换后 120 秒内不再规划；路由按预测最短 TTFT 选节点，取 KV 的耗时计入预测
  • 实验结果与取舍
  • 9 组设定：吞吐 1.10–2.73× Dynamo，丢失 KV 复用少 81–95%；CC 90 agents 时平均端到端延迟 32.2s→7.87s、P95 TTFT 142s→10.2s、吞吐 2.48→5.40 req/s
  • Putnam 例外：decode-heavy 下规划器只留 1–2 节点做 prefill，为保吞吐牺牲 P95 TTFT（224 agents 时 6.24s vs Dynamo 1.13s），但平均端到端延迟仍更低
