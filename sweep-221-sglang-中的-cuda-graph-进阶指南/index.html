SGLang 中的 CUDA Graph 进阶指南

知乎推荐流条目（BBuf 发布、SGLang Team 署名，2026-08-17 发表；读时 134 赞同、204 收藏、3 评论。已据登录态通读原文更正——先前版本为未读原文的提纲版）。SGLang 与 Meta 合作把 CUDA Graph 支持重构为 Runner/Backend 解耦：Runner 管捕获形状、静态 buffer 与 padding，Backend 决定怎么成图——Full 整图、Breakable 可断图（BCG）、TC Piecewise 编译切图。核心是 BCG：在捕获期用标记把不兼容算子留在图外 eager 执行、边界张量固定地址、重放时拷入新值，521 行实现编译路线 1771 行的效果，prefill 建图快 3.8–5.2 倍，已成 prefill 默认；prefill 单测（gpt-oss-120b）Full 1.93 倍、BCG 1.70 倍于 eager。显存一节反直觉：捕获到 chunked prefill 上限反而能把激活峰值压到近零、总显存低于无图基线。

大纲

大纲（据原文通读整理，2026-10-22 更正版）

  • 条目信息
  • 知乎推荐流专栏，BBuf 发布、署名 SGLang Team，2026-08-17 发表；读时 134 赞同、204 收藏、3 评论
  • 工作为 SGLang 与 Meta 合作；结构：TL;DR → 背景 → Runner/Backend 解耦 → BCG 深挖 → Prefill Full → 显存 → 致谢
  • 背景：启动开销
  • 一次推理是许多 GPU 操作的序列而非单个 kernel，CPU 侧反复启动是实打实的成本，延迟敏感型服务尤其明显
  • CUDA Graph 把 GPU 工作录一次、重放多次；难点在执行阶段各异、复杂 kernel、依赖运行期信息的行为，以及捕获本身的时间与显存
  • 架构重构（PR #23906）：Runner 与 Backend 解耦
  • 此前 Decode、Prefill、投机解码各长一套 Runner，捕获形状、静态 buffer、重放逻辑重复
  • Runner 管执行路径状态：捕获形状、静态输入 buffer、注意力元数据、把实时 batch padding 到捕获形状
  • Backend 决定 forward 如何成图：整图 / 可断分段 / 编译切分；Prefill 与 Decode 各有 Runner，投机解码的 Draft 系列 Runner 建在 Decode 之上
  • 三种 Backend
  • Full：每个形状一张整图、无 eager 区、重放启动次数最少；天然适配 decode（每请求一 token，主变量只有 batch size，分桶覆盖）
  • Breakable（BCG）：只捕获图安全区，被标记算子在图段之间 eager 执行；断点在捕获期插入，不靠先 trace 全模型
  • TC Piecewise：torch.compile 全图 trace 后在预注册点切 FX 图、逐段编译捕获；最早的分段方案，BCG 未验证的平台仍在用
  • BCG 深挖
  • 起源：2026-02-21 首个公开实现（PR #19102），prefill 扩展（PR #22218）2026-04-24 合入后成为 prefill 默认；「首创」主张范围限定在开源 LLM 推理引擎的运行期可断捕获机制
  • 机制：标记函数处结束当前图段、eager 执行、新段再起；其返回张量在捕获时留作固定地址的边界 buffer，重放时把新返回值拷入该地址供下一段读
  • 启动优势：编译曾占编译路线建图时间的 78–86%（235B MoE 约 90 秒、GLM-5.2 约 158 秒），BCG 完全免编译，prefill 建图快 3.8–5.2 倍，代码 521 行对 1771 行
  • 兼容与调试：自定义 CUDA/Triton/JIT kernel 不是原生算子，编译路线要包 torch.library 并写假实现才能 trace；BCG 断点可跟随服务逻辑（如与 DP Attention、MoE All-to-All、LoRA、PD 分离等共存）；--debug-cuda-graph 可把整个 forward 包进一个 eager 断点来二分定位问题
  • Diffusion 用例（PR #27436）：对 DiT 重复 forward 同法捕获，单卡 B200 热身后 512×512 Qwen-Image 端到端 6.48→2.45 秒、Z-Image 1.231→0.662 秒；明示边界：只消启动开销，不减 FLOPs
  • Prefill Full：把 prefill 变静态（PR #27988）
  • 难点：batch 同时在总 token 数与请求数两维变化，而图要求两者都固定；部分注意力后端还要运行期元数据
  • 解法：token 分桶 padding + 固定请求槽位（空槽改写为长度 0 的哨兵请求，超出槽位回退 eager）；注意力元数据在图外按 padded batch 重建，目前仅 FA4 与 FlashInfer 支持
  • Padding 代价不对称：padded token 是真实行、要过稠密 GEMM（贵）；空请求槽因变长调度按真实长度算，几乎免费
  • 状态：实验性、需显式开启，官方建议生产用 BCG 或 TC Piecewise
  • Prefill 基准（隔离测 prefill：固定输入长、单请求、关 decode 图；gpt-oss-120b，TP4，4×GB300）
  • 对 eager：Full 1.93 倍、BCG 1.70 倍、TC Piecewise 1.45 倍；BCG 重放还比编译路线快约 17%（后者每次要付 Dynamo guard 与 dispatch）
  • GLM-5.2 上只有 BCG 能捕获（编译路线 trace 不动、Full 不支持其稀疏注意力），为 eager 的 1.60 倍；32 倍 prompt 长度范围内曲线近乎平直，作者读作 launch-bound 的签名
  • 显存：分段捕获的复用与捕获上限
  • 三招复用：同一形状的所有图段共享一个图池；eager 断点处张量用弱引用托管；所有捕获尺寸共享一个按最大尺寸分配的输出 buffer、各自切片
  • 例外：跨 eager 断点传数据的 buffer 地址被下一段绑定，必须常驻并原地更新
  • 结果：GLM-5.2（78 层 MoE）捕获 42 个形状只加约 2.4 GB 图显存
  • 捕获上限比形状个数更重要：捕获梯子若停在最大 prefill 尺寸之下，最大形状仍回退 eager 留住激活峰值、同时还付了小图的常驻显存，总量反而高于无图基线；捕获到 chunked_prefill_size 上限可消掉最坏激活峰值（gpt-oss-120b 0.56→0.001 GB，GLM-5.2 1.55→0.35 GB），总量反而低于无图基线 0.51 / 1.10 GB，且显存变为可预算的固定量
  • 未覆盖（避免过度解读）
  • 无重叠调度专节；DP 仅出现在兼容性清单（DP Attention），TP 仅见于基准配置（TP4）
